# 公网联机与中继服务方案

> 版本：v1.1  
> 状态：阶段一～三已实现，阶段四待生产部署  
> 适用模式：2～4 人肉鸽联机  
> 关联文档：`战斗与联机规则说明.md`、`项目架构设计.md`

## 1. 目标

在现有局域网 ENet 联机基础上增加公网房间能力，同时维持“每名玩家只模拟自己的棋盘”的低成本结构。

本方案采用：

```text
中央房间服务
    ├─ 房间码、玩家名单、端点发布、心跳
    ├─ 优先：房主 ENet UDP 直连
    └─ 兜底：独立 Godot ENet 中继房间进程
```

中央服务不模拟英雄、技能和单位移动。战斗继续在玩家客户端运行；中央服务或中继房间负责房间权威、回合屏障、联合防守路由和玩家生命账本。

## 2. 选择理由

- 当前战斗逻辑已经按“本地棋盘＋可序列化战果”拆分，适合轻量协调服务。
- 2～4 人房间的消息量较小，无需一开始就为每个单位做云端逐帧同步。
- 能直连的玩家不消耗中继流量。
- 无公网 IP、处于 CGNAT 或路由器不支持端口映射时，仍可通过中继进入游戏。
- 后续若需要强防作弊，可将纯数值战斗模拟逐步迁移到权威服务器，不需要推翻房间协议。

## 3. 组件职责

### 3.1 Godot 客户端

- 创建或通过房间码加入公网房间。
- 房主尝试为 ENet UDP 端口建立 UPnP 映射。
- 定期向中央服务发送房间心跳。
- 根据中央服务返回的连接方案选择直连或中继。
- 直连失败时请求整房切换到中继端点。
- 继续使用现有 `MultiplayerRunManager` 执行准备、战果提交、联合防守和生命结算。

### 3.2 中央房间服务

- 生成不可连续猜测的房间码和管理令牌。
- 保存房主公开端点、房间状态、人数和最后心跳时间。
- 为加入者返回当前连接方案。
- 接收中继回退请求。
- 启动并监管独立的中继房间进程。
- 清理超时、关闭或已完成的房间。

首版使用 Python 标准库实现内存型 HTTP JSON 服务。生产部署时由反向代理提供 HTTPS、速率限制和访问日志。

### 3.3 Godot 中继房间进程

- 以 headless 模式运行，一个进程只承载一个房间。
- ENet 服务端是网络 authority，但不占玩家席位。
- 最多接受 4 名玩家。
- 复用 `MultiplayerRunManager` 的房间、回合和联合防守逻辑。
- 不加载主场景、不创建战斗棋盘、不渲染画面。
- 房间关闭、超时或服务停止后退出。

## 4. 连接流程

### 4.1 创建公网房间

1. 房主在大厅选择“创建公网房间”。
2. 客户端启动本地 ENet 服务端。
3. 后台线程执行 UPnP discovery，并尝试映射 UDP 端口。
4. 映射成功：向中央服务发布外网 IP 和端口，房间进入 `DIRECT`。
5. 映射失败：向中央服务申请中继，房间进入 `RELAY_STARTING`。
6. 中继准备完成后，房主关闭本地 ENet 服务端并作为普通玩家连接中继。

### 4.2 通过房间码加入

1. 玩家提交房间码和昵称。
2. 中央服务返回直连或中继端点。
3. `DIRECT`：客户端尝试连接房主，默认超时 4 秒。
4. 直连成功：进入房间。
5. 直连失败：客户端向中央服务请求中继回退。
6. 房主和所有已连接玩家轮询到 `RELAY` 后统一重连中继。

### 4.3 中继切换约束

- 中继切换只允许发生在肉鸽开局前。
- 任意玩家请求回退后，整个房间切换，不允许部分玩家直连、部分玩家走中继。
- 已进入战斗后不自动迁移传输层；断线按现有淘汰/离房规则处理。
- 每次传输切换增加 `transport_generation`，客户端忽略旧代连接结果。

## 5. 房间状态

```text
CREATING
   ├─ UPnP 成功 ─> DIRECT
   └─ UPnP 失败 ─> RELAY_STARTING ─> RELAY

DIRECT ── 连接失败请求 ─> RELAY_STARTING ─> RELAY

DIRECT / RELAY ── 开局 ─> RUNNING ── 结束 ─> CLOSED
```

房间记录至少包含：

```text
room_code
host_token
room_token
status
transport_generation
direct_address / direct_port
relay_address / relay_port
player_count / max_players
created_at / last_heartbeat_at
```

## 6. HTTP JSON 协议

### 6.1 健康检查

```http
GET /health
```

### 6.2 创建房间

```http
POST /v1/rooms
Content-Type: application/json

{
  "host_name": "Player",
  "max_players": 4,
  "direct_address": "203.0.113.10",
  "direct_port": 24567,
  "direct_available": true
}
```

响应包含 `room_code`、仅房主持有的 `host_token`、当前端点和 `transport_generation`。

### 6.3 查询或加入

```http
GET  /v1/rooms/{room_code}
POST /v1/rooms/{room_code}/join
```

加入响应返回房间端点和短期 `room_token`。房间满、已开局或已关闭时拒绝加入。

### 6.4 请求中继

```http
POST /v1/rooms/{room_code}/relay
Authorization: Bearer {room_token 或 host_token}
```

服务端保证幂等；重复请求只返回同一个中继端点。

### 6.5 房主心跳与关闭

```http
POST   /v1/rooms/{room_code}/heartbeat
DELETE /v1/rooms/{room_code}
Authorization: Bearer {host_token}
```

## 7. 分阶段实现

### 阶段一：公网直连基础

- ENet 地址支持域名、IPv4 和 IPv6。
- 房主增加异步 UPnP UDP 映射。
- 暴露连接超时、传输类型和外网端点状态。
- 大厅保留现有 LAN/IP 直连作为调试入口。

验收：

- UPnP 成功时能取得外网地址并发布 UDP 端口。
- UPnP 不可用时明确返回失败，不阻塞主线程。
- 加入超时后能触发回退事件。

### 阶段二：中央房间服务

- 实现无第三方依赖的 HTTP JSON 房间服务。
- 客户端支持创建公网房间、输入房间码加入和轮询状态。
- 房主心跳、离房关闭、过期清理生效。
- 房间服务提供单元测试和本地启动脚本。

验收：

- 2～4 名测试客户端可以通过同一房间码取得一致端点。
- 第 5 名玩家被拒绝。
- 过期房间不再可加入。

### 阶段三：中继兜底

- `MultiplayerRunManager` 增加“不占席位的专用服务端”模式。
- 实现 headless 中继入口。
- 房间服务按需启动中继进程并返回端点。
- 客户端在 UPnP 或直连失败时统一迁移到中继。

验收：

- 房主没有公网映射时，2～4 名玩家仍能进入同一房间。
- 中继服务端不出现在玩家列表中。
- 回合屏障、两段联合防守和来源生命扣除与直连模式一致。

### 阶段四：生产化

- HTTPS、数据库或 Redis 持久化、限流和监控。
- 中继容器编排、容量限制、自动扩缩容。
- 登录身份、封禁、版本门禁和重放审计。
- 战果确认重传、断线重连和房主迁移。
- 对关键战果增加服务端验证，逐步提升防作弊能力。

## 8. 安全边界

- 所有客户端提交均需要长度、类型、范围和数量限制。
- 房主令牌不能返回给加入者。
- 房间码只用于发现，修改房间必须提供令牌。
- 中继端口不能作为管理接口。
- 生产环境不允许直接暴露管理端口，HTTP 服务必须位于 HTTPS 反向代理之后。
- 首版仍信任客户端对本地战斗过程的模拟，只由服务端校验战果结构并维护最终生命账本。

## 10. 首版限制

- UPnP 直连不等同于完整的 UDP 打洞；不支持 UPnP 的对称 NAT/CGNAT 网络会使用中继。
- 传输层只在开局前切换。
- 房间服务首版使用内存状态，进程重启会清空未开始房间。
- 中继负责协调和转发，但不逐帧模拟客户端战斗，因此不能完全防止修改客户端伪造战果。

## 11. 当前实现清单

### 阶段一：已完成

- `public_network_helper.gd`：后台线程执行 UPnP UDP 映射与清理。
- `multiplayer_run_manager.gd`：新增公网直连、中继、连接代次与直连超时状态。
- 手动公网地址可通过 `public_direct_advertise_address` 配置，便于已有端口转发或云主机使用。

### 阶段二：已完成

- `public_room_client.gd`：实现创建、加入、轮询、心跳、中继申请和关闭房间。
- `server/public_room_service.py`：实现房间码、2～4 人容量、令牌鉴权、过期回收和 HTTP JSON 接口。
- 联机大厅同时保留 LAN/IP 调试入口，并增加公网房间码创建与加入入口。

### 阶段三：已完成

- `dedicated_room_server.gd`：实现不占玩家席位的单房间 headless authority。
- 房间服务按需分配 UDP 端口并启动中继进程。
- 创建者通过 `host_token` 在中继中恢复房主权限；其他客户端不能发起开局。
- 直连失败时以 `transport_generation` 为边界整房切换到中继。

### 阶段四：尚未实施

阶段四涉及实际服务器账号、域名、TLS 证书、数据库/Redis、容器平台和监控告警，必须在确定部署环境后实施。当前代码已保留配置边界，不依赖特定云厂商。
