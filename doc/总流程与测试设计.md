## 2. 游戏全流程

### 2.1 总入口流程

```text
启动 Godot
  -> project.godot run/main_scene = res://scenes/start_menu.tscn
  -> StartMenu
       -> 加载/创建存档
       -> 进入 AfkHub
            -> AFK 爬塔/局外养成
            -> 图鉴
            -> 选择肉鸽信物
                 -> 进入 Main 自走棋肉鸽
```

核心 Autoload：

| Autoload | 职责 |
|---|---|
| `DataRegistry` | 启动时读取 `data/*.json`，提供统一数据查询 |
| `SettingsManager` | 游戏设置 |
| `GameManager` | 存档、存档金币、持有角色、肉鸽局内金币/队伍/回合 |
| `BattleManager` | 战斗状态机、波次、单位列表、胜负信号 |
| `ResourceManager` | DP 上限、当前 DP、DP 恢复、技能/部署资源消耗 |
| `Log` | 日志封装 |
| `SynergyManager` | 羁绊统计、数值修正、主羁绊效果 |

### 2.2 数据加载流程

```text
DataRegistry._ready()
  -> load_all()
      -> config.json
      -> classes.json
      -> skills.json
      -> status_effects.json
      -> enemies.json
      -> enemy_scaling.json
      -> synergies.json
      -> waves.json
```

运行时主要访问关系：

| 调用方 | 数据来源 | 用途 |
|---|---|---|
| `ClassDefinitions` | `DataRegistry.get_class_data()` | 生成 `ClassTemplate`，供英雄初始化、招募、图鉴、战力计算使用 |
| `SkillData` | `DataRegistry.get_skill()` 或内置回退 | 技能 CD、DP、倍率、范围、治疗、Buff |
| `EnemyUnit` | `DataRegistry.get_enemy_pool()` | 敌人模板池 |
| `BattleManager`/`RoguelikeManager` | `enemy_scaling.json`、`config.json` | 回合敌人缩放、波次数量、奖励 |
| `SynergyManager` | `synergies.json`、`config.json` | 羁绊定义、层数、默认 modifier |

### 2.3 存档与局外大厅流程

```text
StartMenu
  -> GameManager.load_save() / create_new_save()
  -> change_scene_to_file("res://scenes/afk_hub.tscn")
  -> AfkHubUI
       -> 展示存档金币、持有角色、AFK 状态
       -> CharacterStorageUI 管理持有角色
       -> AfkTowerManager 运行轻量 AFK 战斗
       -> 图鉴入口
       -> 肉鸽入口
```

AFK 爬塔和自走棋战斗是两套隔离模拟：

| 项目 | AFK 爬塔 | 自走棋肉鸽 |
|---|---|---|
| 战斗实体 | 不实例化 `HeroUnit`/`EnemyUnit` | 实例化真实单位 |
| 网格 | 不使用 `GridSystem` | 使用 `GridSystem` |
| 状态机 | `AfkTowerManager.running` + 回合计时 | `BattleManager.BattleState` |
| 战力 | `CombatPowerCalculator.calculate_team_attack()` | 角色属性、AI、技能、羁绊实时计算 |
| 结果 | 推进塔层/奖励预览 | 战斗胜负、肉鸽回合推进 |

### 2.4 AFK 爬塔流程

```text
AfkHubUI 配置小队
  -> AfkTowerManager.configure_party(party)
      -> CombatPowerCalculator.calculate_team_attack()
  -> start_battle(floor, enemy_index)
      -> _spawn_current_enemy()
      -> _process(delta)
          -> 英雄行动：敌人扣血
          -> 敌人行动：播放/状态文本，不造成伤害
          -> 敌人死亡：推进到下一敌人或下一层
```

AFK 关键验证点：

- 配置空队伍时 `team_attack` 至少为 1。
- 点击鼓舞只影响英雄行动频率，不改变永久战力。
- 每层固定 `ENEMIES_PER_FLOOR = 3`。
- 击败第三个敌人后推进层数。

### 2.5 肉鸽局内流程

```text
RoguelikeRelicSelect
  -> GameManager.set_pending_roguelike_relic()
  -> main.tscn
       -> Startup._ready()
            -> 确保存档存在
            -> RoguelikeManager.start_run()
                 -> GameManager.start_roguelike_run()
                 -> recruit_system.reset_run()
                 -> _enter_recruit_phase()
```

当前肉鸽采用“招募/准备与战斗交替”的回合制循环：

```text
进入招募阶段
  -> RecruitSystem.generate_recruit_options(round, party_size)
  -> RoguelikeManager._setup_round_preparation()
       -> BattleManager.setup_battle(..., preserve_player_units=true)
       -> DeploymentSystem.setup_hand(GameManager.get_battle_party_data())
       -> ResourceManager.reset_dp()
  -> 玩家购买、刷新、升级酒馆、部署
  -> 按 F：BattleManager.start_next_wave()
       -> 清空本回合剩余 run_gold
       -> 生成敌人波次
       -> 激活场上英雄 AI
  -> 战斗胜利
       -> 奖励 run_gold
       -> BattleManager.prepare_player_units_for_next_round()
       -> recruit_system.advance_round()
       -> GameManager.advance_roguelike_round()
       -> 回到招募阶段
  -> 战斗失败
       -> run_ended(false)
```

### 2.6 战斗准备与部署流程

```text
BattleManager.setup_battle()
  -> state = PREPARING
  -> player_units/enemy_units 初始化或保留
  -> battle_started.emit()

DeploymentSystem.setup_hand()
  -> 从 GameManager.party 生成 hand_cards
  -> 处理三合一升星
  -> hand_updated.emit()

玩家部署
  -> begin_drag()/点击手牌
  -> GridSystem.can_place_at()
  -> HeroUnit.setup(ClassTemplate, level)
  -> GridSystem.place_unit()
  -> BattleManager.register_player_unit()
  -> BattleManager.unit_deployed.emit()
  -> SynergyManager.recalculate()
```

部署约束：

- 准备阶段部署不消耗 DP；实时部署会按折扣后的 deploy cost 检查/消耗 DP。
- 最多部署 `GameManager.ROGUELIKE_MAX_DEPLOYED_UNITS` 个英雄。
- 肉鸽手牌最多 `GameManager.ROGUELIKE_MAX_HAND_CARDS` 张。
- 三张同职业、同星级、同酒馆等阶的卡会尝试升星。

### 2.7 实时战斗流程

```text
按 F 或测试场景开始
  -> BattleManager.start_next_wave()
       -> state = IN_PROGRESS
       -> GridSystem.spawn_enemy_wave()
       -> 每个 HeroUnit.activate_ai()

每帧
  -> UnitBase._process(delta)
       -> 冷却递减
       -> 状态效果更新
       -> UnitAI.execute(delta)
       -> Debug 圆环刷新

UnitAI
  -> idle: 索敌
  -> moving/waiting: 路径、碰撞预测、等待重试
  -> attacking: perform_attack()

伤害链路
  -> UnitBase._deal_damage_to_target()
       -> _calculate_damage()
       -> 主羁绊伤害前修正
       -> target.take_damage()
       -> 吸血
       -> 主羁绊命中后效果
```

胜负结算：

- 敌人清空且当前波次已完成：`wave_cleared`，最后一波后 `battle_won`。
- 没有存活玩家单位：`battle_lost`。
- 胜利后肉鸽进入下一招募阶段；失败后结束当前肉鸽。

### 2.8 技能与资源流程

```text
玩家选中英雄
  -> Q/W/E
  -> HeroUnit.use_skill(skill_id)
       -> SkillData.get_skill()
       -> 检查 skill_cooldowns
       -> ResourceManager.spend(dp_cost)
       -> _execute_skill()
       -> 设置 cooldown
```

技能效果类型：

- 单体伤害
- AOE 伤害
- 范围治疗
- 自身防御 Buff
- 持续效果定时恢复

### 2.9 羁绊流程

```text
BattleManager.unit_deployed / unit_retreated / battle_started
  -> SynergyManager.recalculate()
       -> 遍历 BattleManager.player_units
       -> 读取 HeroUnit.class_template:
            class_group -> main_*
            stat_tags -> stat_*
            alignment_tags -> alignment_*
       -> 根据 thresholds 计算 active_tier
       -> 根据 layer 计算 scalable_modifiers
       -> 应用到玩家 UnitBase.apply_synergy_modifiers()
       -> ResourceManager.apply_synergy_modifiers()
       -> synergy_changed.emit()
```

主羁绊命中特效当前通过 `UnitBase._get_active_main_effects()` 读取：

- `anmarit`：攻击叠毒并产生 DoT，可在高档位扩散。
- `laferida`：攻击积累自然值，满值触发减速/伤害。
- `naka`：攻击积累燃烧值，点燃目标，高档位对燃烧目标增伤并概率爆炸。

测试场景支持 `SynergyManager.set_test_synergy_override()`，可以绕过场上阵容，手动设置羁绊人数和层数。

### 2.10 Combat Test 流程

```text
打开 combat_test.tscn
  -> CombatTestRunner._start_initial_test()
       -> restart_test()
       -> pause_test()
  -> 默认生成英雄和敌人，但场景暂停
  -> 开发者控制面板：
       -> 开始/暂停/重新开始
       -> 输入 class_id 或 class_id:level 增加英雄
       -> Debug 可视化开关
       -> 测试羁绊设置与生效
```

Combat Test 是手动调试与数值观察工具，不等同于自动化测试。自动化测试应复用其中的场景搭建能力，但需要独立脚本输出断言结果。

## 3. 测试目标与分层

测试体系分三层：

| 层级 | 目的 | 运行频率 | 失败处理 |
|---|---|---|---|
| 冒烟测试 | 确认场景可加载、Autoload 正常、无脚本解析错误 | 每次提交前 | 阻塞合入 |
| 功能单元测试 | 验证独立系统的确定性逻辑 | 修改对应模块时 | 阻塞合入 |
| 集成/数值回归测试 | 验证跨系统流程和战斗数值趋势 | 大改动、发版前 | 需要人工判断阈值 |

## 5. 功能单元测试设计

### 5.1 数据完整性测试

目标：确保 `data/*.json` 与访问器一致。

| 用例 | 断言 |
|---|---|
| `config.json` 可加载 | 必备 key 存在：`max_character_level`、`max_deployment_points`、`roguelike_max_rounds` |
| `classes.json` 全部可生成模板 | `ClassDefinitions.get_template(id)` 返回非空；HP/ATK/DEF/攻速/移速合法 |
| 职业技能引用合法 | 每个 `skill_ids` 都能被 `SkillData.get_skill()` 解析 |
| 敌人池合法 | `EnemyUnit.get_enemy_pool()` 非空；HP/ATK/DEF/范围合法 |
| 羁绊定义合法 | 每个 `thresholds` 升序；modifier stat 非空；main_effect 可解析 |
| 波次/缩放合法 | `enemy_scaling` 数值不为负；波次引用敌人存在 |

建议脚本：`scripts/testing/data_integrity_test.gd`

### 5.2 GameManager 与存档测试

| 用例 | 断言 |
|---|---|
| 新建存档 | `has_active_save = true`，默认金币和角色合法 |
| 加载存档槽 | 当前存档 ID 正确，金币/角色恢复 |
| 肉鸽开始 | `is_roguelike_run = true`，`run_gold` 等于基础值 + 信物修正 |
| 添加队伍卡 | canonical class id 正确，手牌上限生效 |
| 三合一前置数据 | 星级、等级、shop_level 字段存在 |
| 肉鸽回合推进 | `current_run_round` 和 UI 信号同步 |

注意：存档测试要使用临时目录或测试存档槽，避免污染真实 `res://userdata`。

### 5.3 DataRegistry / ClassDefinitions / SkillData 单元测试

| 模块 | 用例 |
|---|---|
| `DataRegistry` | 缺失文件时返回空表并 warning；正常文件排序稳定 |
| `ClassDefinitions` | 别名 `warrior/ranger/mage/priest/rogue` 能 canonicalize；无效 ID 回退 |
| `ClassTemplate` | `get_attack_speed_interval()` 对 0/负攻速返回大值 |
| `SkillData` | 未知技能返回 null；已知技能字段完整 |

### 5.4 ResourceManager 测试

| 用例 | 断言 |
|---|---|
| `reset_dp(initial,max)` | current/base/max 正确 |
| `spend()` | DP 足够时扣除并返回 true，不足时不变并 false |
| `refund()` | 不超过 max_dp |
| `apply_synergy_modifiers()` | `max_dp_bonus` 修改 max_dp，current_dp 被 clamp |
| DP 自动恢复 | 非 PREPARING 且 regen enabled 时按秒恢复 |

### 5.5 BattleManager 测试

| 用例 | 断言 |
|---|---|
| `setup_battle()` | 状态为 PREPARING，波次数正确，列表初始化 |
| `start_next_wave()` | current_wave 增加，状态进入 IN_PROGRESS |
| 敌人清空 | 触发 `wave_cleared`；最后一波进入 VICTORY |
| 玩家全灭 | 进入 DEFEAT |
| `preserve_player_units` | 下一回合保留 HeroUnit 并恢复部署位置/生命 |

建议用最小假单位或 `CombatTestRunner` 生成单位，不依赖完整 UI。

### 5.6 GridSystem 测试

| 用例 | 断言 |
|---|---|
| 坐标转换 | `grid_to_world()` 与 `world_to_grid()` 可逆近似 |
| 部署区域 | 非部署区不可部署 |
| 占用表 | `place_unit()`、`remove_unit()` 正确维护 occupancy/all_units |
| 范围查询 | `get_units_in_range()` 按 team 和半径筛选 |
| 路径/移动预留 | 目标格被占时不能 reserve；取消移动释放 reservation |
| 碰撞预测 | 地面圆相交时返回 hit_unit，不相交返回空 |

### 5.7 UnitBase / HeroUnit / EnemyUnit 测试

| 用例 | 断言 |
|---|---|
| 英雄初始化 | 按 class template 和等级缩放属性 |
| 敌人初始化 | 按模板设置 HP/ATK/DEF/类型颜色 |
| `take_damage()` | 至少造成 1 点伤害；死亡后注销单位 |
| `heal()` | 不超过 max_hp，满血时返回 0 |
| 姿态切换 | 驻扎防御/射程变化，定身职业 move_speed=0 |
| 普攻 | 冷却设置正确，目标 HP 变化 |
| 技能 | DP 消耗、冷却、伤害/治疗/Buff 生效 |
| 状态效果 | 中毒、燃烧、自然值按 tick 更新并可过期 |

### 5.8 UnitAI 测试

| 用例 | 断言 |
|---|---|
| 无目标 | 可移动单位向敌方方向推进 |
| 有目标且在射程 | 状态进入 attacking 并执行攻击 |
| 目标死亡 | target 清空并回到 idle |
| 治疗职业 | 优先选择受伤友军 |
| 索敌优先级 | `NEAREST/LOWEST_HP/HIGHEST_ATK/RANDOM` 行为符合模板 |
| 等待状态 | 路径被阻挡时进入 waiting，重试后能恢复 |

AI 测试应使用固定随机种子，避免 `RANDOM` 导致不稳定。

### 5.9 DeploymentSystem 测试

| 用例 | 断言 |

## 6. 集成测试与数值回归设计

### 6.1 Combat Test 自动化扩展

现有 `CombatTestRunner` 已能：

- 重置测试战斗。
- 批量放置英雄/敌人。
- 开始/暂停。
- 添加英雄。
- 开关 Debug。
- 覆盖测试羁绊。

建议新增 `combat_matrix_test.gd`：

```text
for class_id in ClassDefinitions.get_all_class_ids():
  for enemy_template in EnemyUnit.get_enemy_pool():
    restart_test()
    spawn_hero(class_id, level=1, fixed_pos)
    spawn_enemy(enemy_template, fixed_pos)
    start_test()
    模拟 N 秒
    记录：
      hero_damage_done
      enemy_damage_done
      skill_cast_count
      death_time
      remaining_hp
输出 latest/combat_matrix.json
```

回归策略：

- 不要求每个数值完全相等，使用阈值。
- DPS/HPS 变化超过 15%-25% 时标记为需要审查。
- 生存时间变化超过 30% 时标记为需要审查。
- 关键职业或 Boss 敌人设置更严格阈值。

### 6.2 肉鸽流程集成测试

最小闭环：

```text
加载 main.tscn
  -> Startup 自动 start_run
  -> 购买一个可负担招募项
  -> 部署一名英雄
  -> start_next_wave()
  -> 强制清空敌人或使用弱敌池
  -> 验证 battle_won
  -> 验证回到 recruit phase
```

需要避免真实长时间战斗。建议构造测试敌人池：

```gdscript
[{ "name": "OneHitDummy", "hp": 1, "atk": 0, "def": 0, ... }]
```

### 6.3 AFK 集成测试


### 6.4 数据导出/平衡回归

已有 `tools/balance/export_balance.py` 可作为平衡数据导出基础。建议输出：

平衡脚本不替代运行时测试，但能帮助发现数据异常。

## 9. 验收标准

### 9.1 冒烟测试验收

- 所有主场景可 headless 加载。
- Autoload 初始化无错误。
- 所有 UI 脚本节点路径存在。
- `DataRegistry` 可解析全部 JSON。

### 9.2 功能测试验收

- 核心管理器状态转换可预测。
- 数据访问器对非法 ID 有回退或明确失败。
- 战斗胜负判定不依赖 UI。
- 羁绊 modifier 与主羁绊效果都可被独立验证。
- AFK 与自走棋战斗互不污染状态。

### 9.3 回归测试验收

- 数值波动在阈值内。
- 超阈值项必须记录为“预期改动”或修复。
- 新增职业、技能、羁绊、敌人时必须补数据完整性测试。
